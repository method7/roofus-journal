## What we did

- Named the project Roofus and agreed the aim: learn agentic AI by building a
  framework for running a small business.
- Agreed the working model: Simon directs, agents build, Claude trains and
  reviews (decision 0001).
- Created the private monorepo `method7/roofus` (decision 0002).
- Looked at how the Method7 site already pulls in shared code, and proposed
  publishing the journal the same way (decision 0003, accepted).
- Wrote the house rules every agent reads first (`CLAUDE.md`), borrowing
  Method7's: UK English, no em-dashes, plain English.
- Opened the first tasks as GitHub issues.

## What we learned

- A decision journal is not just documentation. Agents start every session
  with no memory, so the journal is how the project remembers.
- Small details of existing infrastructure decide architecture. Whether the
  shared package was public or private changed the whole publishing plan.

## Later the same day

  Method7 projects (issue #7). The no-em-dash rule turned up in five of them
  and was checked automatically in none.
- Built our first skill, `uk-house-style` (decision 0005). A test with a small

## What we learned, round two

- Merging is approving. Once the journal mirror exists, a merge is a publish.
- Agents report success in the same tone whether or not they thought of
  everything. The audit agent removed hostnames, and missed that the whole
  security section was the sensitive part.

## What we learned, round three

- **Verify, don't trust.** Every agent report sounded the same whether or not
  it had caught everything. Each one was checked before it was passed on, and
  the checks found something most times.
- **Copied settings break quietly.** The branch protection copied from Roofus
  to `house-rules` asked for checks that did not exist there, so nothing could
  ever have merged. It looked fine until it was compared with reality.
- **Give each key the smallest reach that works.** The publishing key opens one
  repository and can only be used from `main`. The first attempt put it
  somewhere wider, and it was replaced within a minute.
- **Check that a merge happened.** One pull request we believed was merged was
  still open. Nothing leaked, because the publish step had its own safeguard,
  which is the argument for having more than one.
- **Names carry meaning.** A pull request titled with `draft: true` read as a
  draft pull request. Plain words would have avoided it.
- **Someone else's skill carries their taste.** The most popular design skill
  lists "near-black with an acid-green accent" among the looks to avoid. That
  is Method7's actual brand. A skill is a set of opinions, so the brief sets
  the direction and the skill only supplies the working method.
- **Good checks find problems beyond their own task.** The design agent,
  checking what the website's link checker would reject, found a published
  link to a private file that no earlier review had noticed.

- Looked at three published skills for taking the AI sound out of copy, and

  different licence. Another tells the agent to run a script on every edit.
- Wrote that skill, `humanise-copy`, in `method7/house-rules`, and copied it
  into Roofus. Its first rule is that an edit never adds a fact. A fresh agent
  tested it on three samples. It cleaned up the AI-sounding one, lightly
  edited a paragraph from a Method7 guide, and left a good journal paragraph
  alone. This section is its first real job.

## What we learned, round four

- **Text an agent reads can try to give it orders.** A web page, an email or
  a skill file can contain a line written to an AI. This is called prompt
  injection, and it is the main security risk once agents read things written
  by outsiders. So Claude told the agents that read outside skills to treat
  any instruction inside them as something to report, never to follow. The
  humanise-copy test included a hidden instruction, and the agent reported it
  rather than obeying it.
- **A brief can be wrong too.** A brief is the written instructions an agent
  is given. One agent's brief said the Method7 site held one stray em-dash;
  it held seventeen. Another brief left out that a script
  needs the site running. Both agents said so instead of guessing.
- **The reviewer makes mistakes as well.** Claude tested that the
  share-image script stops safely when something goes wrong, but the first
  attempt never actually broke anything, so it proved nothing and had to be
  run again. And one late change went onto a pull request that had already
  been merged, so it was left out and needed a second pull request.
- **The review step lives in Claude's habits, not yet in Roofus.** The checks
  done before each pull request reached Simon are written down nowhere an
  agent or a new session would find them.

## What I learned, round five

- **Written rules aren't locks.** The rules in `CLAUDE.md` are instructions
  the AI reads and usually follows. Permission settings are enforced by
  Claude Code, and branch protection by GitHub, so the AI cannot simply
  decide to ignore them. "Agents never merge" was only written down: my agents use Simon's
  GitHub login, so GitHub could not have told them apart from Simon. Simon
  counts this among the strongest lessons so far:

  > Deny rules match command patterns, so they're guardrails, not a vault.
  > A determined workaround could get round them. That's why GitHub stays
  > the final lock.

- **Test a reviewer with something it should pass.** Catching planted flaws
  proved the review skill could find problems. Only the sound pull request
  showed it could not yet tell a problem from an unproven claim.
- **A habit of style can cause a habit of error.** Three times, drafts
  written about Simon from the outside gave Simon pronouns Simon had never
  stated. Reviews caught each one, but changing who narrates removes most
  of the cause.
