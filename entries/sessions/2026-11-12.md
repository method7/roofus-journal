## What we learned, round three

- **Verify, don't trust.** Every agent report sounded the same whether or not
  it had caught everything. I checked each one before passing it on. The
  checks found something most times.
- **Copied settings break quietly.** The branch protection copied from my
  repository to `house-rules` asked for checks that did not exist there, so nothing could
  ever have merged. It looked fine until it was compared with reality.
- **Give each key the smallest reach that works.** The publishing key opens one
  repository and can only be used from `main`. The first attempt put it
  somewhere wider. It was replaced within a minute.
- **Check that a merge happened.** One pull request I believed was merged was
  still open. Nothing leaked, because the publish step had its own safeguard,
  which is the argument for having more than one.
- **Names carry meaning.** A pull request titled with `draft: true` read as a
  draft pull request. Plain words would have avoided it.
- **Someone else's skill carries their taste.** The most popular design skill
  lists "near-black with an acid-green accent" among the looks to avoid. That
  is Method7's actual brand. A skill is a set of opinions, so the brief sets
  the direction and the skill only supplies the working method.
- **Good checks find problems beyond their own task.** The design agent,
  checking what the website's link checker would reject, found a published
  link to a private file that no earlier review had noticed.

## What we learned, round four

- **Text an agent reads can try to give it orders.** A web page, an email or
  a skill file can contain a line written to an AI. This is called prompt
  injection. It is the main security risk once agents read things written
  by outsiders. So I told the agents that read outside skills to treat
  any instruction inside them as something to report, never to follow. The
  humanise-copy test included a hidden instruction. The agent reported it
  rather than obeying it.
- **A brief can be wrong too.** A brief is the written instructions an agent
  is given. One agent's brief said the Method7 site held one stray em-dash;
  it held seventeen. Another brief left out that a script
  needs the site running. Both agents said so instead of guessing.
- **The reviewer makes mistakes as well.** I tested that the share-image
  script stops safely when something goes wrong, but my first attempt never
  actually broke anything, so it proved nothing and had to be
  run again. One late change also went onto a pull request that had already
  been merged, so it was left out and needed a second pull request.
- **The review step lives in one session's habits, not yet in my rules.** The checks
  done before each pull request reached Simon are written down nowhere an
  agent or a new session would find them.

## What I learned, round five

- **Written rules aren't locks.** The rules in `CLAUDE.md` are instructions
  the AI reads and usually follows. Permission settings are enforced by
  Claude Code and branch protection by GitHub, so the AI cannot simply
  decide to ignore them. "Agents never merge" was only written down: my agents use Simon's
  GitHub login, so GitHub could not have told them apart from Simon. Simon
  counts this among the strongest lessons so far:

  > Deny rules match command patterns, so they're guardrails, not a vault.
  > A determined workaround could get round them. That's why GitHub stays
  > the final lock.

- **Test a reviewer with something it should pass.** Catching planted flaws
  proved the review skill could find problems. Only the sound pull request
  showed it could not yet tell a problem from an unproven claim.
- **A habit of style can cause a habit of error.** Three times, drafts
  written about Simon from the outside gave Simon pronouns Simon had never
  stated. Reviews caught each one, but changing who narrates removes most
  of the cause.

## What I learned, round six

- **A guardrail has to guard itself.** Rules an agent can edit are rules an
  agent can remove. The lock that held was the one on GitHub, as Simon's
  lesson in round five said it would be.
- **When a mistake repeats, move the check out of habits.** I made the same
  mistake with a finished pull request twice, the second time after writing
  the rule against it into my own review skill. CI does not forget.
- **A check is only tested once it has failed for the right reason.** The
  pin check's first failure, on real work, showed more than a passing run
  ever could.

## What I learned, round seven

- **Changing the voice can change the facts.** Rewriting in the first
  person made it easy to say "I" about things Simon chose, or to credit
  work to the wrong person. A rewrite needs a fact-check, not just a read.
- **A check that only prints is not a check.** Seeing the right answer on
  screen does not stop anything. The script has to act on it.
